# Owner-requested objective content

Generic review responses use the separate [write and approval display boundary](generic-action-display.md). Full validation source remains on the exact dedicated routes described below; diagnostic display references and existing public narratives remain available to current tenant readers.

This prepared contract lets the original reviewing owner associate one exact Shopify title/description request with one active, explicitly enforced saved objective and one selected candidate in a succeeded diagnostic review. The owner chooses the destination, retained product reference and replacement text. Preparation creates one existing `customer_facing_publish` approval and one connection write together. Approval and apply remain separate actions.

This is an owner-requested content change associated with a goal. It does not generate an autonomous business proposal, establish commercial readiness, measure goal progress or authorize financial activity. Tags, images, product status, price, refunds, advertising, replenishment, other providers, paid models and automatic execution are outside this contract. Default profit-first and every non-null financial/stock limit, including zero, still stop execution before credential preparation.

## Trust and source validation

The report is server-recorded diagnostic history, not independently authenticated immutable proof. The existing guarded completion path fences application workers and terminal updates; a privileged store writer can still forge mutually consistent rows or replace history through other privileges. Canonical digests detect observed change relative to a saved binding. They are not signatures.

The server loads one exact tenant/job with a bounded response and requires `objective_prepare`, `succeeded`, the exact v1 payload, original actor equality, current account session version, deterministic zero-provider/model/AI posture and the derived enqueue identity. It reconstructs the whole diagnostic report using the retained report timestamp and snapshot-revision reference, compares canonical whole results, and separately recomputes current typed input and current active objective policy. The historical timestamp/revision is used only for reconstruction, never as current authority. Object keys are sorted; arrays retain their order. Unsupported values, accessors, depth and byte excess fail closed.

Raw relevant source identities, duplicates and tenant scope are checked before canonical filtering. The selected canonical opportunity must be present and map to exactly `Thin product title` or `Thin product description`, `customer_facing_publish`, one exact typed product evidence ID and the detector's exact product/issue reference. The current retained product must still have that issue. Missing-image and product-status opportunities cannot become content instructions. Whole-report reconstruction rejects changed or missing diagnostic safeguards, fabricated readiness, unsupported nested candidates, derived-ID changes and malformed scope.

Retained products have no verified account/import provenance in the current product mapper. The editor labels that limitation and requires explicit owner confirmation of the destination account and product ID. This contract does not claim a provider-current content baseline or independently prove product membership in that account. Preparation performs no credential decryption, refresh, test, sync, model or provider request.

The requesting and applying account must be the unique current owner record matching the report's original actor and account `sessionVersion`, active and without a required password change. Two logins at the same account version may use the report. Existing jobs do not retain a login `jti`, so this is not original-login provenance. The existing separate owner decision can be made by another currently valid owner; it remains exactly bound and independently checked.

## API and optimistic preview assertion

All three routes are owner-only, tenant-bound and rate-limited together to 20 requests per minute. They use the existing workspace lock, current owner/session recheck and CAS. POST uses existing CSRF protection and a 24,000-byte request cap. Exact reconciliation reads do not rely on the newest-50 Connection Centre list.

- `GET /api/objective-content/context?jobId=...&opportunityId=...` returns `runvara-objective-content-context/v1`, the server source, `sourceRevision`, exact existing manual-content target reference, selected objective/candidate, retained product, policy blockers and the trust/provenance notice. Unavailable targets fail rather than selecting another account. Financial blockers may be shown while allowing preparation.
- `POST /api/objective-content/requests` accepts exactly `requestId`, `jobId`, `opportunityId`, `sourceRevision`, `target`, `productId`, `title`, `description`, and `confirmedDestinationProduct: true`. No report body, source object, origin, policy envelope, ignored approval IDs or financial authority is accepted.
- `GET /api/objective-content/requests/{requestId}` returns one bounded exact request projection, or `found: false` from that observation. No query overrides are accepted.

`sourceRevision` is an opaque canonical digest produced by context. The client echoes it only as an **untrusted optimistic comparison assertion**. POST independently reloads and reconstructs the full source and compares its freshly derived revision. It never uses the assertion to fill missing data, grant authority or manufacture proof. This closes the context-to-POST retained-product/report change gap without promoting client source objects. Omitted, malformed, forged, foreign and stale assertions fail before saving.

POST and reconciliation return `runvara-objective-content-request/v1`, workspace/request/requester identity, `found`, a common exact saved write projection plus server-selected `origin: owner_objective_content` and full source, and `sourceStatus`. Source status is `current`, `changed` or `unavailable`; terminal history remains history and never grants a new apply. The response is capped at 64 KiB. The target's settings revision remains an open-draft check; it is not stored as a credential-generation proof.

The in-memory draft keeps a stable request ID. A lost response, cancellation or absent lookup does not prove the original POST cannot commit. Any error once persistence is attempted, including a post-save guard/acknowledgement failure, is returned as `503 OBJECTIVE_CONTENT_SAVE_UNKNOWN`; the client must reconcile the same exact ID and intent. There is no automatic POST retry, new ID or source rebinding. After an absent exact lookup, the owner may explicitly retry the same ID only after a fresh context matches the original source revision and target and the owner renews the acknowledgement; a late original commit and that exact retry coalesce through deduplication/CAS. Pending same-intent reuse revalidates its exact own approval and source. Same ID with different source revision, requester/epoch, account, family or normalized text conflicts. The manual endpoint and manual reconciliation cannot confirm a v2 request.

## Stored v2 envelope and own approval

The existing `objectivePolicyProposal` field contains `runvara-objective-dispatch-proposal/v2`. It retains the common workspace/write/provider/operation/input/account/requester/approval-kind/policy bindings, with explicit `origin: owner_objective_content`, server source, independently bound approval ID and stable approval digest. Its own digest is included in the existing approval payload and entire claim identity. Manual v1 serialization, claim reconstruction, origins and optional recorded action bytes are unchanged.

The source schema is `runvara-objective-content-source/v1`. It contains selected objective ID/revision/definition digest; exact job ID and stable identity digest; report ID; canonical whole payload/result digests; original actor/account version; the original 32-hex typed fingerprint; selected opportunity ID and canonical/resource-mapping digest; retained product ID and content-baseline digest; and `approvalSourceDigest`. New content digests are 64-hex SHA-256. Stable job identity excludes incidental `updated_at` touches but includes creation/completion identity and deterministic posture.

The only private fingerprint exception is the exact approval created by this request. Its fresh ID must be absent before insertion. At later checks the server validates all approval identities/scopes before removal, then requires one unique own row with exact type, requester, revision, payload/envelope relationship and bound stable fields. Pending state and the normal separate decision history are validated exactly; arbitrary decision/history edits, rejection, duplicates or missing approval fail. Only expected decision and execution bookkeeping transitions are permitted.

After those checks, a cloned comparison view removes that one row, including its count. The original report is never rewritten or marked fresh by this exception. `approvalSourceDigest` additionally binds the whole remaining ordered approval collection, including fields omitted by the older typed fingerprint. Other approval changes still stale the request. A second different request from the same original report normally needs a fresh review, because it cannot remove the first request's approval.

## Dispatch and save boundaries

Preparation reads the exact job once for validation and again when preparing the actual commit. Apply rereads before credentials and at both existing phase checks. Each phase completes its job read before the final narrow exact-revision workspace authority read. Local source, requester, policy, write and approval checks run again after awaits; current-time restrictions are enforced before provider dispatch. Workspace revisions cannot replace job reads because history is stored separately.

These are observation boundaries, not an atomic job/workspace transaction. A pause cannot recall an already-submitted provider request; a privileged change immediately after the last read is outside the claimed guarantee. A failed check after a claim never clears that claim or authorizes replay. Two-replica conditional saves retain the existing at-most-one phase submission behavior.

V2 preparation and dispatch opt into `save(..., { ownedSnapshot: true, beforeCommit })`. The store takes a deeply owned save snapshot before archive/queue awaits. A synchronous guard checks both live inputs and the private snapshot immediately before serialization. This prevents in-place source mutation from entering a pre-dispatch CAS as the approved source, while preserving legitimate final approval/result/work bookkeeping and existing automation run handles. Default saves retain their existing behavior.

After actual transport submission, mutable source/owner eligibility is no longer a new gate on recording a confirmed response. The original exact write, approval decision, phase claim and admission history remain pinned through the private final snapshot and acknowledgement, including exact final approval bookkeeping. A later source disappearance or clock expiry can make current source status stale while the submitted action remains known successful. Final CAS still cannot overwrite another replica's intervening workspace change. A lost final acknowledgement or uncertain result never permits provider replay.

## Data usage and storage limits

Context adds one exact job read; a new preparation adds two; each successful apply adds three, with two existing narrow workspace authority reads after its phase job reads. A reconciliation adds one exact job read when a saved v2 request exists. Pending deduplication performs source validation and exact status resolution without a new write/approval. Job status responses are capped before parsing at 16 KiB; report envelopes at 160 KiB, allowing duplicate detection with `limit=2`; each report is separately limited to 64 KiB. The v2 envelope stays within 8 KiB.

These response caps do not bound database computation or whole-workspace reads/writes. The route still uses the existing full current workspace inside the mutation lock. Owned saves add a full deep copy before asynchronous archival and keep the existing full-state primary CAS/mirroring work. There is no new separate pre-copy workspace byte cap; the existing primary-state serialization/commit ceiling is 2 MiB. Copying incurs additional transient memory and CPU proportional to that state, plus existing archive/serialization buffers. This slice adds no wider database projection, ledger, RPC, grant or SQL migration.

FileStore payload/result ingress is defensively copied. Its jobs remain volatile and disappear after restart; absent history fails closed. FileStore can support non-durable preparation/testing, but its production dispatch refusal remains unchanged.

## Outcome compatibility and rollback

The separately prepared [reviewed action forward union](reviewed-action-outcomes.md#objective-origin-content-forward-union) prospectively captures successful v2 actions with their real objective origin, full pinned source/proposal and independently checked stable approval. It uses the existing final save. Old completed actions without that context remain unavailable; optional size/shape failure preserves the known result. Explicit owner-selected measurement and owner publication remain separate, and require the forward storage marker. Full private evidence stays inside the server; exact-version browser evidence uses an explicit redacted v2 display schema. This preparation does not apply the forward migration or release the application.

Deploying or rolling back remains separately authorized. An executor retaining the prepared v1 policy-envelope rejection guard denies pending/ready/processing v2, unknown versions and changed operations/providers before credentials. Keep the envelope, histories and claims intact; never relabel v2 as manual, strip fields, reset uncertainty or regenerate old approvals. Current production object `d32da62d0e7935597638266d44d88ae5e066d51f` predates that guard and is **not a safe rollback target once v2 records exist**. A safe rollback retains the rejecting guard or disables v2 preparation/execution.

Synthetic API, source, actual dispatcher/transport, owned-save and adapter tests cover the boundaries above. They are not a live customer/provider demonstration, PostgreSQL concurrency proof or release authorization. Browser, aggregate regression, database compatibility and eventual exact-head CI results are recorded separately.
