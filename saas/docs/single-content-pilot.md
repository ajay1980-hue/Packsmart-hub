# Dormant single-request description pilot

This is local code and test preparation. No production issuer, HTTP activation
endpoint, live scope, deployment, migration application or settings change is
included. Ordinary startup supplies no capability. `createPacksmartServer`
accepts only the opaque capability returned by trusted `createContentPilot`
composition; serializing, copying or submitting that object cannot grant access.

The broad governed-record producer gate must remain closed. The narrow capability
binds workspace, connection, account, product, operation, request ID, requester,
exact input digest, settings revision and expiry. Owner/session, tenant, exact
approval, objective-policy, financial/stock restrictions, audit, rate admission,
workspace CAS and protected receipts remain mandatory. Profit-first remains
blocking without qualified evidence. Objective-generated requests stay closed.

## Versioned content and evidence

| Format | Input | Source/context | Protected admission/receipt |
| --- | --- | --- | --- |
| Historical manual | Existing title and plain description | v1 | v1 |
| Historical objective | Existing title and plain description | v2 | v1 |
| Description pilot | `runvara-description-edit/v1` | v3 | v2 |

The description pilot uses `runvara-single-content-pilot/v2`. Its exact input
contains `schema`, `productId`, `operation`, `baselineHtml`, `baselineUpdatedAt`,
`paragraphHtml`, `replacementText` and `descriptionHtml`. Ordered request identity
and approval digests include every field. The exact baseline, selected paragraph
and full result are retained in the protected source. No title field is accepted.
The mutation contains only `id` and `descriptionHtml`; its response selects only
product ID and errors. Historical bytes and hashes are not translated.

One uniquely matching explicit paragraph is selected. Only its inner content is
replaced with escaped plain text; its opening/closing tags, attributes, and all
surrounding HTML bytes remain unchanged. The implementation slices the original
string; it never parses and serializes the document. Line endings, whitespace,
entities, other paragraphs, lists and formatting outside the selection survive.
The representative synthetic fixture includes several paragraphs, a list,
formatting, attributes, comments, CRLF, accented text and an emoji. It is not a
simpler substitute for a real product. The real Grey Mailing Bags product has not
been read or changed, and its eligibility has not been established.

The bounded HTML grammar supports explicit balanced paragraphs, div/section,
headings, ul/ol/li, common inline formatting, links, images, breaks and comments.
Attributes must be quoted when they have values. Ambiguous duplicate paragraphs,
implicit closures, malformed nesting, raw script/style content, tables, templates
and foreign content are refused. Unsupported content is never flattened. Baseline
and result each have a 12,000-byte ceiling; replacement text has a 4,000 UTF-16-unit
ceiling. Existing source/receipt/storage limits can refuse a smaller combined
request before dispatch; no existing quota was increased.

Updated readers accept old and new evidence. They display HTML as escaped text.
A browser normalizes CRLF for display only; displayed text never reconstructs
request authority. Description receipt choices use the action label “Shopify
description change” rather than claiming a recorded product title. Older readers
reject an unsupported version; they do not reinterpret its signed content.

## Protected storage and forward SQL

Admission now passes a private, nonserializable permit from the dispatcher into
the real storage adapter. The adapter rechecks scope, expiry, pause and exact
reservation contents before its existing transaction. A raw descriptor or copied
capability cannot open the broad storage gate. Finalization of an already
submitted result remains possible after pause/expiry.

`server/supabase/prepared/description-edit-contract.sql` is a forward SQL draft,
not an applied migration. It is generated by
`node server/scripts/prepare-description-edit-sql.mjs` from unchanged predecessor
functions and the private helper source. It adds a matching SQL paragraph grammar,
new identity/source/envelope validation, and compatible receipt consumers. It
preserves existing signatures, grants, table guards, quotas, locks and ledger rows;
new helpers have no public/anon/authenticated/service-role execution grants.
It neither changes enforcement mode nor rewrites historical rows.

The draft remains outside production migration history. It has now compiled and
run in an explicitly approved, temporary PostgreSQL 17.11 cluster on loopback with
SCRAM authentication and durability enabled. No production database was used.
The disposable harness checks historical bytes, JS/SQL preimages, 25 shared HTML
and Unicode/size-boundary cases, 12 UTC timestamp cases, mixed formats, and
description dispatcher modes. Those modes include real transactions with
synthetic provider responses, lost ACKs after commit, exact reconciliation and
refusal. The prepared SQL and historical migration files required no changes.

The upgraded consumer harness runs the entire historical consumer suite after
the forward SQL, plus publication/correction/withdrawal for manual input with and
without objective policies, objective v2 sources, and description v3 sources.
It checks exact immutable snapshots and tests actual current and baseline reader
modules against SQL responses. The baseline reader rejects the v3 marker even
for historical records. Compatible readers must be deployed before the SQL marker
changes; an unchanged old reader cannot participate in that mixed fleet.

## Provider race and activation limit

The pinned [Shopify 2026-07 ProductUpdateInput](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/ProductUpdateInput)
contains optional title and description fields, but no documented comparison
version/digest field. The [productUpdate arguments](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/productUpdate)
also expose no conditional-write parameter. Metafield compare-and-set support
protects metafield writes; it does not make a product description update atomic.
No documented atomic conditional description update was found. This is a
source-based finding, not a guarantee that no other provider mechanism exists.

After durable reservation, the pilot reads the bound product's exact description
and updatedAt, then performs the final fresh local authority check. A changed or
unavailable baseline stops the send. A competing description edit after that read
can still be overwritten by the full-description mutation. Title omission removes
the pilot's title overwrite; it does not remove the description race. The pilot
remains default-off and makes no silent acceptance of that residual risk.
Provider normalization of accepted HTML is also not verified by an ID-only ACK;
the receipt proves the submitted input and provider-confirmed product ID, not a
subsequent byte-identical provider readback.

## Attempts, pause and rollback

An opaque capability permits one attempt. Durable executing state, phase claim,
CAS and receipt admission fence replay and replicas. Reconstructing a process
capability cannot restart an executing/failed/uncertain request. Lost provider
responses never justify a resend. Lost storage ACKs use the existing exact
fingerprint reconciliation path; committed-but-lost ACKs are tested separately
from refused commits. Unknown outcomes remain closed.

`pauseContentPilot` is process-local. It does not recall an in-flight request or
stop other processes by itself. Fleet-wide pause/rollback requires retaining the
existing database guard and compatible receipt readers/writers, stopping every
issuer/producer and accounting for admitted work. Removing the capability or
using a v1-only receipt adapter refuses new description sends. Reverting SQL,
disabling enforcement or downgrading all readers is not a supported rollback.
Local separate-process concurrency and forced process termination are covered by
the disposable SQL suite. Distributed fleet pause/rollout behavior and database
server/power-loss recovery remain outside that local proof.

## Local evidence and remaining gates

`description-edit.test.mjs` covers selection, exact fields, old/new records,
scope, stale baseline/settings/approval/session, expiry, financial restrictions,
complete valid objective rejection, concurrency and restart simulations.
`description-edit-store.test.mjs` exercises the real adapter over synthetic
transport, including committed-but-lost reserve/final ACKs and capacity refusal.
HTTP and JSDOM tests cover exact approval, closed producers and escaped history.
Those files provide local mock/unit/browser results. Separate opted-in
`content-execution-receipt-postgres.mjs` and `description-edit-postgres.mjs` runs
provide actual PostgreSQL proof; their provider and PostgREST transports remain
synthetic. They do not establish hosted Supabase/PostgREST or live Shopify parity.
The prior 4,131-test run belongs to the old prototype and is not evidence for this
phase. Current run results and file hashes are recorded in the workspace evidence
directory.

The approved validation used the official EDB PostgreSQL 17.11-3 Windows x64 ZIP,
verified against its published SHA-256 before execution, and locked `pg` 8.16.3
dependencies installed with lifecycle scripts disabled in a disposable directory.
It used no Windows service, administrator privileges, firewall change, permanent
PATH change, or extra system prerequisite. Exact commands, hashes, results and
verified shutdown/cleanup evidence are retained in the task evidence directory.
Reproduction requires another approved disposable runtime and an exact baseline
reader fixture: export `saas/server/lib` from commit
`b010e5546b10dbf08bb2386177fdbbba5d4a4b1a` and set
`RUNVARA_OLD_READER_ROOT` to the export root. The harness also requires its existing
`OUTCOME_ALLOW_DISPOSABLE_TEST_DB=1` opt-in and guarded loopback database URL.

Before any live activation: review reader and fleet rollback compatibility,
resolve or explicitly review the provider
race, obtain and approve the exact real baseline/result, and separately authorize
live work. Code/test approval here does not authorize any of those live actions.
