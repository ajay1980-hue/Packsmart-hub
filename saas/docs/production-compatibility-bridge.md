# Production compatibility bridge

This preparation starts from the existing production baseline. It is a reader and rejection bridge; it does not enable the cumulative objective, receipt, recovery, or routing features.

Ordinary unmarked integrations keep their existing provider queries, request counts, permissions and approval flow. Newer stored execution authority is opaque to this runtime. Unsupported provider/operation or objective-policy envelopes are rejected before credentials or a new provider submission. Existing completed results remain completed; uncertain attempts are never replayed.

Applicable enforced or unknown objective policies block execution. Policy identity includes exact values, presence, arrays and types, while JSON object order is immaterial. The original bounded snapshot is pinned across awaits. An owned save snapshot and synchronous final guard prevent shared-object changes during persistence from authorizing a different request. CAS still governs durable revisions. This is not a substitute for a fresh remote read or predecessor termination.

Existing eBay retry deadlines and review-required markers survive reconnect, first-sync and failure paths. Unknown or malformed holds require review. Reconnection does not prove a throttle expired. The bridge does not introduce a Retry-After parser or new marker producer.

Newer pending read debt, order-source and recovery markers conservatively defer the affected provider before Doctor, sync or reconnect resets. Malformed or excessive retained envelopes also defer. Deferral preserves records and prior successful-read evidence; it is not a completed import or permission to retry. An unmarked workspace continues using the baseline adapters.

Generic action and approval responses use nested display allowlists. They preserve already-public exact content, identifiers, input digests, narratives, evidence and history. Private policy envelopes, claims, security epochs, future completion context and AI governance remain server-side. Display projection never changes stored records or supplies authority. Saved changes with an unsupported operation remain visible without an execute control. A recognised operation with a newer authority envelope still fails the backend compatibility guard.

## Rollout boundary

Publish and validate the exact candidate on a separate branch. Required checks include all server tests and static guards, all four disposable PostgreSQL workflows, production-container smoke tests, existing browser flows and actual compatibility screenshots at phone and desktop widths with enlarged text. Synthetic passes do not establish live production health.

Before a production change, verify the current serving commit and application readiness through permitted first-party evidence, reconcile competing branches, and establish the rollback target. Do not bypass blocked browser health access. A successful Render deployment event alone does not prove predecessor processes have terminated.

Before enabling any newer state producer, establish predecessor termination and reconcile outstanding or uncertain jobs. The existing drain helper can resolve before a pending worker claim returns; a shutdown-start log or elapsed timer is not proof that all claims settled. The bridge does not change that lifecycle behavior or introduce an operational pause.

This bridge is only a compatibility step before forward capabilities. It is not a certified rollback target after any forward SQL, protected-receipt, outcome-consumer or recovery capability activates. The earlier production baseline must not be used as rollback after newer authority is stored. A later release needs readers compatible with its exact installed schema, persisted contracts, active producers, quotas and uncertain attempts.

No SQL, database grants, credentials, provider scopes, service settings or feature activation are included. The five prepared cumulative migrations require their own reviewed installation/access/activation plan. Protected receipts and recovery also have distinct approved preparation limits and lifecycle rules; this bridge neither creates nor removes that evidence.
